Can a ChatGPT share link be guessed?

UUIDv8 entropy check of chatgpt.com/share/<id> · five own samples plus 4,565 public links · 2026-11-05

Not reportable

No. The link ID holds 62 random bits behind a timestamp. With a botnet at 10 million requests per second, and the exact second the link was made, the expected time to one hit is 360 million years.

The theory of limited entropy is half right and does not matter. The random field is 62 bits, not 78, because the second segment is sub-second time and the third is a shard id. Two public write-ups documented this layout before 2026-11-05. A test on 4,565 public share links from 26 months finds no bias, no counter and no serial structure in the 62 bits. An independent adversarial review in a second, independent analysis returned upheld with corrections. The corrections are on this page.

Adversarial review, same day: upheld with corrections. The sub-second field matches the share API clock within 4.3 to 5.3 ms on all five links, and 4,565 public share IDs pass per-bit, byte and serial tests.

Anatomy of one link ID

The first of the five samples, colored by field. The five samples match two public analyses (about 284,000 and about 440,000 IDs) and a corpus of 4,565 public share IDs tested in this repository (research/large-sample.md) on every boundary.

6aec6686-4d9c-83ed-b905-76a831afef31
32 bits · Unix seconds
2026-11-05 11:20:38 UTC. Time of link creation, not of the chat. Known to anyone who sees the link, and guessable by anyone who knows when the owner shared.
14 + 2 bits · sub-second
Fraction of a second, then two bits that are always 00. The review compared it with the share record's own create_time: all five match within 4.3 to 5.3 ms. Chance that five random values all land in a 12 ms window: 2.5e-10.
4 bits · version 8
RFC 9562 custom layout. Fixed.
12 bits · node id
3ed = node 1005, 3eb = node 1003. Shard ids in deliberate decimal ranges. Seven values (nodes 1000 to 1006) are current, and 81 values appeared over the format's lifetime. About 20 were active at a time in 2025. Same across accounts, so not account-bound.
2 bits · variant
Always 10, so the fourth group starts with 8, 9, a or b. Fixed.
62 bits · random
The only secret. Every test on the five samples is consistent with a cryptographic random source.

How long would guessing take?

Expected years to one targeted hit at 10 million requests per second

Log scale. Each bar is one attacker knowledge scenario. The hollow bar is a hypothetical weak design with 32 random bits, shown for contrast. The dashed line is the age of the universe. Node count is taken as 3, the attacker-favorable floor; the real count is 7 or more.

ScenarioSearch spaceYears at 10⁷ req/s

Untargeted guessing fares no better. With 1,000 links created per second platform-wide and a botnet running for a year, the expected number of hits is 0.0000014. At 100 links per second and 100,000 requests per second, untargeted guessing starts to work near 32 random bits. At the botnet rate above, the threshold is near 43. A targeted guess starts to work at about 44 to 53 random bits (one day to one year at 108 requests per second) under attacker-favorable assumptions. The field has 62. With the seven current nodes the second-known space is 278.8 instead of 277.6, which makes the search harder, and the chart keeps the attacker-favorable three-node figure.

The endpoint is a clean existence oracle, and the owner's own share opens without login. Neither fact matters while the space is 277.6.

About the "6% hit rate" blog post. A Substack article claims that random v8-shaped ids hit real shares 6% of the time. A 6% rate would need 7 to 14 bits of total entropy. The post counted an HTTP 200 page that lacked the 'Can't load shared conversation' text as a hit, a test that misfires on Cloudflare challenge pages. It gave no request count and showed no real link. On 2026-11-05 the page returned 404 for a nonexistent id. The claim is unsupported.

Adversarial review: upheld with corrections

A second, independent analysis reviewed this page with the brief in HANDOVER-adversarial-review.md. Its report is review/REVIEW.md. It re-derived the layout, reran the arithmetic, ran its own bit tests on 692 GitHub ids and on the 4,565, and read the share records of the five own links.

ItemFinding
LayoutConfirmed. The 14-bit field matches the server create_time on all five links. A counter reading of segment 2 is refuted.
Node countCorrected. Seven nodes (1000 to 1006) issue share ids since 2026-07, 81 over the lifetime. With 7 nodes the second-known space is 278.8. The error ran in the author's favor.
MathEvery number on this page reproduces. Flip point for a targeted guess: about 44 to 53 random bits (one day to one year at 108 requests per second).
GeneratorConfirmed on first-order tests. State recovery (Mersenne Twister, xorshift, LCG) is untested and cannot be tested from one account: it needs hundreds of consecutive outputs from one worker, and other users' draws interleave.
Source attributionCorrected. The "181,000 ids" figure was a timestamp check on conversation ids, not a bit-distribution study. The bit-balance claim is one sentence over about 284,000 mixed ids.
EndpointContradicts a third-party 403 report cited in the research notes (public-record.md section 6, now annotated with the measured 200). Deleted and nonexistent ids return the same error code.

Answers to the open questions

  • Timestamp meaning: link creation. Confirmed by the share record's create_time. The first four links are 28, 9 and 19 seconds apart.
  • 83eb / 83ed: shard ids 1003 and 1005, two of the seven current nodes 1000 to 1006. Shared across accounts and OpenAI products. Not account or user bound.
  • Same-second ids: three same-second pairs in the corpus, one on the same node. They share only the second and the node.
  • Counters or correlations in the 78 bits: 16 of them are time. The other 62 show none.
  • Re-share, update, delete behavior: not tested. These need a logged-in session. Note from the review: a deleted id and a nonexistent id return the same error code.
  • Unauthenticated access to own link: yes, confirmed by the probe.

When would this become reportable?

Only with one of three proofs, each possible on the researcher's own links: a predictor that names the 62-bit field of the researcher's next share link before it exists, a collision or reuse of the 62 bits across two links, or a derivation of the 62 bits from known inputs. If the bits were predictable, the severity would be P2 for targeted reads and P1 for mass harvest, with a $20,000 base for a critical ChatGPT finding. Pure guessing against the live service never qualifies. OpenAI's Bugcrowd brief excludes brute force and asks for a working proof of concept. RFC 9562 section 8 already says that UUIDs must not be the only access control. A timestamp plus 62 CSPRNG bits is the standard answer to that rule.
