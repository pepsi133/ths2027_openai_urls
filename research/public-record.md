# Public record: the random bits behind OpenAI's UUIDv8 identifiers

Compiled 2026-11-05 from web search, direct fetches of primary sources, GitHub code search
(`gh search code`), and read-only queries against the Wayback CDX API and the Common Crawl
index. No request was made to chatgpt.com other than one fetch of `/robots.txt`. No account
was created, nobody at OpenAI was contacted, no ID was enumerated.

Established context (not re-derived here): since 2024-08-30 ChatGPT conversation and share IDs
are UUIDv8 laid out as 32 bits Unix seconds | 14 bits sub-second + 2 zero bits | version
nibble 8 | 12-bit "node" in decimal ranges (0x3e8 = 1000 ...) | 2 variant bits | 62 random
bits. Sources: https://hindsig.ht/blog/decoding-chatgpt-ids/ and
https://github.com/RyanDFIR/unfurl/pull/292 .

---

## 1. Does any open-source library produce exactly this layout?

**Answer: No. No public library, IETF draft example, or OpenAI repository matches the
32/14+2/8/12/2/62 layout; it is a custom, in-house UUIDv8. The random source therefore cannot
be read off any library's code.**

Evidence:

- IETF draft-peabody-01 (the only draft with a 32-bit timestamp option for v8) uses a
  different split: "timestamp_32 ... The most significant 32 bits of the desired timestamp
  source", then a 16-bit `timestamp_48` field ("set to 0 for a 32-bit source"), version, a
  12-bit `time_or_seq`, variant, an 8-bit `seq_or_node` and a node of 54 bits. Node rule:
  "the node MUST NOT be set to all 0s" and "In most scenarios the node SHOULD be filled with
  pseudo-random data."
  https://www.ietf.org/archive/id/draft-peabody-dispatch-new-uuid-format-01.html
- Draft-01/02 UUIDv7 used 36 bits of seconds plus two 12-bit `subsec` fields, not 32+14.
  https://datatracker.ietf.org/doc/html/draft-peabody-dispatch-new-uuid-format-02
- Draft-04's UUIDv8 example (Appendix A.3): "32 bit custom-epoch timestamp (seconds elapsed
  since 2020-01-01 00:00:00 UTC)", "16 bit exotic resolution (~15 microsecond) subsecond
  timestamp encoded using the fractional representation", "58 bit random number", "8 bit
  application-specific unique node ID", "8 bit rolling sequence number". Custom epoch and
  16-bit fraction rule it out. Same draft: "Implementations SHOULD utilize a cryptographically
  secure pseudo-random number generator (CSPRNG)" and "Care SHOULD be taken to ensure the
  CSPRNG state is properly reseeded upon state changes, such as process forks."
  https://datatracker.ietf.org/doc/html/draft-peabody-dispatch-new-uuid-format-04
- Python `uuid6` (oittaa/uuid6-python) `uuid8()`: 48-bit ms, 12-bit `subsec_a`, 8-bit
  `subsec_b` (`value * 2**20 // 10**6`), 54 random bits from `secrets.randbits(54)`. Not a
  match. https://raw.githubusercontent.com/oittaa/uuid6-python/main/src/uuid6/__init__.py
- Python `uuid7` (stevesimmons): docstring promises "36 bits of whole seconds / 24 bits of
  fractional seconds ... 14 bits of sequential counter / 48 bits of randomness" but the code
  packs 48-bit ms + `os.urandom(2)` + `os.urandom(8)`. Not a match either way.
  https://raw.githubusercontent.com/stevesimmons/uuid7/main/uuid_extensions/uuid7.py
- CPython 3.14 `uuid.uuid8(a, b, c)`: 48/12/62 custom fields; missing fields filled by
  `random.getrandbits(48)`, `random.getrandbits(12)`, `random.getrandbits(62)` (Mersenne
  Twister, not CSPRNG). Docs: "By default, a, b and c are not generated by a cryptographically
  secure pseudo-random number generator (CSPRNG)." `uuid4()` and `uuid7()` use `os.urandom`.
  This is the one mainstream v8 primitive whose default random source is predictable, but it
  carries no timestamp; an application would have to compute `a`, `b` itself and pass only
  `c=None`. https://docs.python.org/3.14/library/uuid.html ,
  https://raw.githubusercontent.com/python/cpython/3.14/Lib/uuid.py
- `uuid-utils` (Rust-backed Python): "Version 8 UUIDs using user-defined data"; caller
  supplies all 128 bits. https://pypi.org/project/uuid-utils/
- PyPI `uuidv8`: "custom_a 48 bits random, custom_b 12 bits random, custom_c 62 bits random",
  no timestamp. https://pypi.org/project/uuidv8/
- Go `github.com/ash3in/uuidv8`: `TimestampBits32/48/60`, "Random 12-bit value" clock
  sequence, "Random 6-byte node identifier"; different layout, v1.2.0 published 2024-12-26,
  after the OpenAI format appeared. https://pkg.go.dev/github.com/ash3in/uuidv8
- Go `google/uuid` v7 comment: "12 bits of (fractional nanoseconds) >> 8" (12-bit, not 14).
  https://github.com/google/uuid/blob/master/version7.go
- GitHub code search in the `openai` org for `uuid8`, `uuidv8`, `UUIDv8`, `new_v8`, `uuid_v8`
  (run 2026-11-05 with `gh search code --owner openai`): zero hits. Nothing in OpenAI's public
  repositories generates or documents this layout.

Observation relevant to the random source: the pre-2024-10-28 sub-second field capped at
15258 = (1e9 - 1) >> 16 shows the generator took `time_ns() % 1e9 >> 16`; the 2024-10-28
switch to a flat 0..16383 distribution is consistent with a change to `ns * 2**14 // 1e9` (a
binary fraction, as hindsig.ht guesses: "I can't confirm that from the IDs alone") or to a
random 14-bit value. Neither public analysis distinguishes the two.

Confidence: **high** that no public library matches; **n/a** for the random source (unknown).

## 2. Has OpenAI or an OpenAI engineer published anything about ID generation?

**Answer: Nothing found. No blog post, talk, changelog entry, API doc or GitHub issue from
OpenAI describes the UUIDv8 layout, the node field, the 2024-08-30 switch or the 2024-10-28
sub-second change.**

Evidence:

- Searches for OpenAI + "uuidv8"/"uuid8"/"conversation id design" return only the two
  third-party analyses (hindsig.ht, unfurl PR #292). The search summary: "These are inferences
  from observed IDs, not official OpenAI documentation."
- OpenAI's public API uses different, prefixed IDs (`conv_...`) with an explicit `created_at`
  field; nothing there mentions embedded timestamps.
  https://developers.openai.com/api/reference/resources/conversations/methods/retrieve
- OpenAI's PostgreSQL scaling talks (Bohan Zhang, POSETTE 2025 / PGConf.dev 2025) and the
  Microsoft write-ups cover replicas, PgBouncer and a Cosmos DB migration for shardable
  workloads but say nothing about ID generation.
  https://techcommunity.microsoft.com/blog/adforpostgresql/scaling-postgresql-at-openai-lessons-in-reliability-efficiency-and-innovation/4428483
- The ChatGPT release notes (help.openai.com article 6825453) could not be fetched (403 to
  non-browser clients); third-party timelines for 2024-08/2024-10 list Canvas (2024-10-03),
  Advanced Voice on macOS (2024-10-30) and ChatGPT search (2024-10-31), nothing about IDs or
  shared links. https://www.testingcatalog.com/year-in-review-key-chatgpt-features-released-in-2024
- The hindsig.ht post reached Hacker News as item 50292503 ("New research shows how to
  extract a timestamp from ChatGPT IDs") with 1 point and 0 comments; no insider commentary.
  https://news.ycombinator.com/item?id=50292503
- community.openai.com threads about conversation IDs ("Accessing ChatGPT Threads via API
  with UUIDs from Web Interface", id 707883) have no staff reply on format.

Confidence: **high** (absence after targeted search of the obvious channels).

## 3. Per-bit statistics, datasets of collected IDs, public corpora of share links

**Answer: Nobody publishes a raw ID dataset or per-bit tables. hindsig.ht reports one
sentence of per-bit statistics ("evenly distributed at every bit position") over ~284k IDs.
The largest public ID-bearing corpora are the Wayback Machine (order 10^5 share URLs) and the
ShareChat dataset (102,740 ChatGPT conversations with a `url` column). Common Crawl has
nothing for chatgpt.com because robots.txt blocks CCBot.**

Evidence:

- hindsig.ht: "To figure out the layout, I collected about 284,000 unique ChatGPT IDs from the
  Wayback Machine, Common Crawl, and my own URL corpus." On the 62 bits: "After the two variant
  bits, the remaining 62 bits are evenly distributed at every bit position across the sample.
  I didn't find any more structure in there." No dataset link; code link is to Unfurl only.
  https://hindsig.ht/blog/decoding-chatgpt-ids/
- unfurl PR #292: "None of about 181,000 archived conversation IDs has an embedded time later
  than its first archive capture." Tests use "synthetic IDs built to the documented layouts";
  the collected IDs are not in the repo. https://github.com/RyanDFIR/unfurl/pull/292
- Digital Digging (Henk van Ess with Nicolas Deleur, 2025-08-01): "110,000 ChatGPT
  conversations preserved in ... Wayback Machine"; Wayback director Mark Graham: the archive
  has not received or honored "requests for (large scale) URL exclusion" of chatgpt.com/share.
  https://www.digitaldigging.org/p/chatgpt-confessions-gone-they-are
- ShareChat (arXiv 2512.17843, Dec 2025): 142,808 conversations from five platforms, 102,740
  from ChatGPT, collected "May 2023 to Aug 2025" by matching "chatgpt.com/share/*" in the
  Wayback Machine and rendering with Selenium. Dataset card lists core fields "platform, url,
  turns_count, message_index, role, plain_text", so share URLs (hence IDs) appear to be
  included; license CC BY-NC 4.0. https://arxiv.org/html/2512.17843 ,
  https://huggingface.co/datasets/tucnguyen/ShareChat
- Google indexing episode (2025-07/08): Fast Company found "nearly 4,500" indexed share URLs;
  OpenAI's CISO called discoverable sharing "a short-lived experiment"; OpenAI then de-indexed
  roughly 50,000 links. https://cybersecuritynews.com/chatgpt-conversations-search-engines/
- Own read-only measurements (2026-11-05; archive.org was intermittently "Temporarily
  Offline", so these are lower bounds):
  - Wayback CDX `chat.openai.com/share/*`: 9 CDX pages; 3 pages retrieved yielded **10,008
    unique UUIDs, all version 4** (nibble histogram: 10008 x '4'), captures 2023-2026.
  - Wayback CDX `chatgpt.com/s/*`: 73 CDX pages (not downloaded). `chatgpt.com/share/*` page
    count unavailable during the outage.
  - Common Crawl indexes CC-MAIN-2024-10, 2024-46, 2025-30, 2026-43: `chatgpt.com/share/*`
    returns `{"pages": 0}`. CC-MAIN-2023-40 `chat.openai.com/share/*`: 402 unique v4 IDs.
    Cause: https://chatgpt.com/robots.txt has "User-agent: CCBot / Disallow: /" while
    allowing `/share/` and `/s/` to other crawlers. hindsig.ht's Common Crawl IDs must come
    from links on third-party pages, not from crawled share pages.
- Corpus estimate: 1-3 x 10^5 distinct UUIDv8 conversation/share IDs are publicly
  reconstructable from Wayback alone (consistent with 181k, 110k, 102,740 and 284k figures
  from four independent collectors). GitHub code search and Reddit/X add low tens of
  thousands more but with heavy overlap.

Confidence: **high** on absence of a published per-bit dataset; **medium** on corpus sizes
(archive outage, overlapping collections).

## 4. Prior bug-bounty or security write-ups on predictable ChatGPT identifiers

**Answer: None found. No public report, accepted or rejected, claims that ChatGPT
conversation, share, file or GPT IDs are predictable. The only quantitative guessing claim
is the Substack post, which is unsupported. The 2026-10 share-link P1 was XSS, not IDOR.**

Evidence:

- Substack "How To EASILY! Guess ChatGPT's Share Links" (2025-10-05): claims "approximately"
  6% hit rate for v8-shaped random GUIDs vs 0.4% for fully random GUIDs, "from our hour or so
  of testing", "All 109 discovered shares followed UUID v8 format", "Most discovered shares
  were deleted/private", "No timestamp encoding detected". No attempt count, no example of an
  accessible hit, and a success criterion (HTTP 200 without "Can't load shared conversation")
  that other tools contradict (see section 6). The 0.4% baseline for random 122-bit GUIDs is
  itself impossible, which marks the methodology as broken.
  https://promptjourneys.substack.com/p/easily-guess-chatgpts-share-links
- Parameter / Bugcrowd P1 (reported 2026-10-18, fixed 2026-10-26, $5,000): a share page ran
  attacker JS via MathLive postMessage + CSP-allowed YouTube JSONP, then called
  `GET /backend-api/conversations?...&limit=20` and
  `GET /backend-api/conversations/<conversation-id>?num_turns=2` with "Authorization: Bearer
  <victim token>". IDs were obtained from the victim's own list, not guessed: "Guessable share
  or conversation IDs: Not addressed." https://www.parameter.ai/labs/we-found-a-gap-at-openai
  , https://dev.to/randomchaos/a-chatgpt-share-link-leaked-your-private-conversations-4oia ,
  https://thehackernews.com/2026/10/a-shared-chatgpt-link-could-run.html
- OpenAI Bugcrowd brief excludes "Attacks that may degrade, disrupt, or negatively impact
  services or user experience (e.g., denial of service, brute force, password spraying, spam,
  fuzzing, specifically unless authorized by OpenAI's security team). This includes brute
  forcing our APIs." No wording about UUIDs or predictable identifiers was found. (Page needs
  JS; text via search snippets.) https://bugcrowd.com/engagements/openai
- OpenAI's 2026-11-02 bounty update lists example payouts including "High-severity IDOR
  resulting in reading a file uploaded to user's Project" (attributed to Prism, not ChatGPT)
  with no write-up. https://openai.com/index/rewarding-defenders-with-bigger-bug-bounties/
- Custom-GPT file/instruction exposure (Dark Reading, 2024): OpenAI's position was "by
  design"; not an ID issue. https://www.darkreading.com/cloud-security/chatgpt-exposes-instructions-knowledge-os-files
- Searches for "ChatGPT IDOR conversation id", "share id enumeration", "backend-api/files
  IDOR", "gizmo id IDOR" on Medium, HackerOne, Bugcrowd, dev.to: no matching disclosure.

Confidence: **medium-high** (public bounty disclosures are sparse by design; a rejected report
could exist without a trace).

## 5. Context: the ShareGPT dataset (2023) and the older share-link format

**Answer: ShareGPT (sharegpt.com) was a third-party Chrome extension with its own 7-character
nanoid IDs, unrelated to OpenAI's URLs. OpenAI's own shared links launched 2023-05-24 as
random UUIDv4 and stayed v4 until 2024-08-30; every archived chat.openai.com/share ID I
sampled (10,008) is v4.**

Evidence:

- ShareGPT repo `app/lib/utils.ts`: `customAlphabet("0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ
  abcdefghijklmnopqrstuvwxyz", 7); // 7-character random string` (62^7 ~ 3.5e12 space).
  README: "As of 2024, ShareGPT is no longer actively being maintained", "API access has been
  discontinued"; repo archived 2026-09-02. https://github.com/domeccleston/sharegpt
- HF `RyokoAI/ShareGPT52K`: "approximately 52,000 ... 90,000 conversations", "scraped via the
  ShareGPT API before it was shut down"; `id` examples "2wtLdZm", "Og9h3C1", "zi8VbDz" (the
  sharegpt.com nanoids). No chat.openai.com/share links.
  https://huggingface.co/datasets/RyokoAI/ShareGPT52K
- OpenAI shared links: release note 2023-05-24; first public example
  `https://chat.openai.com/share/5c14a304-1b7f-4fb9-b400-21e65ad545bb` (version nibble 4).
  https://virtualizationreview.com/articles/2023/05/25/chatgpt-shared-links.aspx
- Trend Micro (2023-07): "anyone who obtains the shared URL can access its content."
  https://www.trendmicro.com/en_us/research/23/g/chatgpt-shared-links-and-information-protection.html
- Own CDX sample: 10,008 unique `chat.openai.com/share/<uuid>` IDs, 100% version 4; Common
  Crawl CC-MAIN-2023-40: 402 unique, all v4.

Confidence: **high**.

## 6. Rate limiting and bot protection on chatgpt.com/share and backend-api/share

**Answer: Share pages are served anonymously behind Cloudflare; the HTML embeds the
conversation as React Router "turbo-stream" data, while `backend-api/share/...` returns 403
without a browser session. Measured 2026-11-05 on the owner's own links: plain `curl` with a
Firefox User-Agent string received HTTP 200 and the full share JSON, and 404 on an altered id.
The 403 report above describes datacenter IPs behind Cloudflare, not the endpoint's policy.
Datacenter IPs routinely get 403/429; Retry-After headers are
sent. No published figure for the numeric threshold exists.**

Evidence:

- chatgpt-share-reader: a share page "looks empty to a plain HTTP fetch, and its backend API
  answers 403 without a browser session"; data is in "React Router's turbo-stream format";
  "The format is undocumented and can change without notice."
  https://github.com/roykollensvendsen/chatgpt-share-reader
- ChatPeek README: fetches "using the same headers a private browser tab would send", retries
  "HTTP 429/5xx ... backing off 5s then 10s, or honouring a Retry-After header". Source
  `check_fixture_links.py`: "Datacenter IPs (e.g. CI runners) hitting chatgpt.com behind
  Cloudflare routinely get these, so they must not be reported as stale.
  _TRANSIENT_STATUSES = {403, 408, 425, 429, 500, 502, 503, 504}" and "Statuses that
  genuinely mean the share no longer exists. _GONE_STATUSES = {404, 410}". This contradicts
  the Substack's "200 + 'Can't load shared conversation'" success test.
  https://github.com/vl3c/ChatPeek
- openai/codex issue #17860: on Linux "every request to chatgpt.com/backend-api/ returns HTTP
  403 with a Cloudflare JavaScript challenge page"; reporter attributes it to the rustls TLS
  fingerprint, so TLS JA3/JA4 fingerprinting is active on the backend-api path.
  https://github.com/openai/codex/issues/17860
- GPT_scraper (older unofficial client) is "not supported anymore"; users report 403 from
  Cloudflare JS challenges. https://github.com/rodolflying/GPT_scraper
- Cloudflare returns rate limits as 429 / Error 1015 and challenges as 403 with
  `cf-mitigated: challenge`. https://devmarde.com/blog/cloudflare-blocking-ai-bots
- robots.txt allows `/share/` and `/s/` to general crawlers (so the pages are meant to be
  fetchable) but has no Crawl-delay. https://chatgpt.com/robots.txt
- ShareChat's authors fetched ~10^5 share pages with Selenium over months and report no
  blocking, which bounds the sustainable rate at roughly one page per few seconds per IP.

Confidence: **medium** (qualitative; thresholds unpublished).

## What would settle the 62-bit question

Legal, no third-party data, no enumeration against chatgpt.com:

1. **Own-account corpus with known ordering.** Create N conversations (and share links) in
   quick succession from one owned account, record exact wall-clock time and the order. Compare
   consecutive IDs: shared node value, monotone seconds, sub-second deltas versus measured
   deltas. Any correlation between successive 62-bit tails (same high bits, small XOR
   distance, linear relation) indicates a non-CSPRNG. Repeat from two accounts at the same
   second to test per-node vs global state.
2. **Test for a counter in the tail.** Fire bursts of requests within one 1/16384-second tick
   (parallel API/web calls from the same account). If the 62 bits contain a sequence counter
   (RFC 9562 method 1: "the most significant, left-most, bits of rand_b MAY be leveraged as
   additional counter bits"), IDs created in the same tick will share a prefix and differ by
   small increments.
3. **Statistical battery on the public corpus.** Pull the ~10^5 v8 IDs from Wayback CDX +
   ShareChat `url` column (both public, both archives), extract the 62-bit tails, group by
   node and by day, and run NIST SP 800-22 / Dieharder subsets (frequency, runs, serial
   correlation, lag-k autocorrelation, birthday spacing). hindsig.ht only reports per-bit
   balance, which a Mersenne Twister also passes; serial tests are what discriminate.
4. **Mersenne Twister reconstruction attempt.** If section 1 above identified Python's
   `random.getrandbits(62)` as the generator (CPython 3.14 `uuid8` default), 624 consecutive
   32-bit outputs recover MT state. 62-bit draws consume two 32-bit words each; with ~312
   consecutive IDs from one process one can test state recovery offline against the
   remaining IDs of the same burst. A failure to reconstruct is itself evidence for a CSPRNG
   or for interleaved processes.
5. **Process/worker fingerprinting.** Check whether tails cluster by node and by time window
   in a way that suggests many worker processes each with its own PRNG (fork without reseed;
   draft text: "reseeded upon state changes, such as process forks"). Duplicate or
   near-duplicate tails across different seconds would be decisive.
6. **Ask through the sanctioned channel.** File an informational Bugcrowd report describing
   the layout and asking whether the 62 bits are CSPRNG-derived; OpenAI's answer, even a
   closure as "informational", becomes the public record.
7. **Negative control.** Run the same battery over the 10,008 archived v4 IDs (122 random
   bits, almost certainly `os.urandom`) to calibrate the tests before interpreting v8 tails.
